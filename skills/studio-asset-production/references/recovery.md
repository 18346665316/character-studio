# 失败恢复与实际效果检查

## 先确定哪一层失败

| 观察 | 下一步 |
| --- | --- |
| 没有任务ID、连接中断或提交超时 | 核对本地任务、generation.json与请求日志；可能已扣费。未知提交不自动重发 |
| 有远程ID、仍生成中/查询超时 | 使用原任务追踪，不建立同一候选的新任务 |
| 明确服务失败、429、认证失败 | 留存错误；按用户范围与服务条件决定是否继续。停止批量扩量，不循环重试或切换服务 |
| 已有成功原图，抠图/打包失败 | 原图在 `.local/props/jobs/ID/inputs/original.png`，先看原图。普通继续可能复用成功原图，但相同算法问题会再次失败 |
| 原图画错主体、带文字、结构错误 | 调整描述/参考或换候选；抠图不能把菜篮变成摊位，不把包成功当成内容正确 |
| 处理成功但游戏里看不清 | 同一人高比例比较目标镜头、轮廓与背景干扰，不靠增大源图分辨率承诺解决 |
| 镂空或投影混合导致清理拦截 | 先查看拟移除位置和结果；不能统一归因主体用了品红，更不能简单抬高阈值 |

Studio会保留成功原图与远程回执。手工修改job状态、generation.json、清单哈希或删除回执来重试会破坏来源，不这样做。

## 普通物件内部背景点选

失败任务有原图时，UI任务记录提供“修正背景（不生图）”。适用于封闭区域内接近单色背景的像素，例如提手中间。它不是笔刷分割、任意蒙版或生成式修图；点到非背景会被拒绝。

API顺序：

1. `GET /api/props/recovery-source?id=JOB_ID` → `job,title,size,source_sha256`，原图尺寸供坐标换算。
2. `POST /api/props/recovery-preview`：`{job,source_sha256,background_points:[[x,y]]}` → `image`数据URL、`preview_sha256`、processing。最多64个原图整数坐标点。看原图再选点，不能直接套用竹筐样例坐标。
3. 将返回PNG显示到深浅背景，检查主体、孔洞与细边；API返回图不会自动为AI完成视觉判断。浏览器CSP不允许data URL图片时转换为blob URL，不降低CSP。
4. 满意后 `POST /api/props/recovery-save`：同一数据加 `preview_sha256` → 新素材manifest。标记变化先重新预览；源图指纹不一致重新加载。同一预览重复另存复用相同版本。

这条路径保留默认清理阈值和缩放残色检查；人工确认的背景点只是增加背景连通区域种子。源任务保持failed，新的候选用 `provenance.source_job` 关联，状态接口提供 `recovered_kits`。另存不会自动更新项目引用，使用set_asset显式选择。完整原图/回执/提示词/背景点随包保存。墙体/院落不走此入口。

## 看什么才叫可用

按本次使用范围逐项看：

- 原图：主体与数量是否正确，关键结构/视角是否成立，是否含多余地面、文字、投影。
- 处理：深浅底上的边缘、内部孔洞、细枝与碎屑；整体不缺失不代表每条细边完好。
- 实际镜头：相同人高比例下，轮廓能否支持本次用途。普通陈设、明确交互对象与近景展示需要不同程度的辨识。
- 组合/引擎：需要时检查连接、重复纹理、角色前后遮挡和通行。物理测试通过不能代替美术判断，静态截图也不能证明行走和碰撞正确。

记录只要能回溯：项目/需求/任务/候选ID、共同参考指纹、采用版本、具体结果和下一步。必要时另存独立JSON，但这是执行证据，不是新的Studio发布或审批数据模型。一次三件成功只能说明这一批，不计算为普遍稳定率。
