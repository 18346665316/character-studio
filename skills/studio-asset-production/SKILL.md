# Studio 素材生产

目标是得到适合指定游戏用途的素材，并根据实际阻碍打磨 Studio。图片数量、任务 complete、文件检查通过、Demo 面积均不能代替可用性判断。

## 找到当前环境

先定位当前 Studio 仓库（有 `studio`、`pipeline/panel.py`）及适用的仓库指令。读取 `.local/panel/server.json` 获取候选服务地址，实际访问确认后使用，不硬编码端口或项目 ID。没有运行服务时，在仓库运行 `./studio panel`，使用返回地址。不要更改图片服务配置来绕过失败。

使用现有 UI 或 HTTP API；批量操作可用 [scripts/studio_api.py](scripts/studio_api.py)。脚本以 `--root` 指定仓库，支持 JSON GET/POST 和文件下载，无自动重试；POST 记录发出意图与结果，token 自动读取且不输出。接口说明见 [references/api-and-data.md](references/api-and-data.md)。不要直接改项目、任务、清单或素材包文件来模拟流程成功。

## 决定生产条件

读取用户指定项目的 `baseline`、需求项、当前素材及任务；没有指定且有多个相关项目时先查现有内容再澄清。延续用户已经确定的用途、风格和复用范围。不要把明代题材、特定模型、三件一批或某个像素尺寸写成通用要求。

制作前明确：实际用途和类别、目标游戏镜头、标准人高比例、统一风格与光照、共同参考、是否需要连接/通行/动画。具体规则与可填写示例见 [references/style-and-prompts.md](references/style-and-prompts.md)。缺少美术标准时先用现有条件和代表性候选校准，不强制建立庞大风格文档。

用户要求生产即按其已授权范围执行；仅要求设计 skill、写提示词或只读检查不授权新增付费请求。已获生产授权时不重复询问。未给数量时用少量代表性素材起步，观察结果再决定扩充。

## 完成一轮生产

1. 通过项目接口创建/更新需求；生成时传 `studio_context`，让后端继承当前基准。需要画风参考时直接使用物件工作台或对应生成接口的 `reference`。项目快捷生成不会自动带入你私下选定的参考图。
2. 提交前保存此次请求意图和共同参考指纹；取得任务 ID 后立即记录。跟踪已有任务，避免不确定提交和无条件重跑脚本导致重复费用。失败分流见 [references/recovery.md](references/recovery.md)。
3. 先查看原图是否画对主体、结构、视角和用途；再看处理图在深浅背景上的边缘、孔洞与碎屑。不通过时判断是换候选、调整提示词、背景修正还是能力限制。代码不能自动修正任意造型、历史或绘画问题。
4. 按标准人高设置实际比例，调整锚点与必要碰撞，另存版本。人高、像素、画布和物理尺寸的区别见数据参考。不要把整张图高当作作物或桥梁的真实高度。
5. 将代表性素材放在同一目标镜头检查搭配、辨识度，以及用途所需的连接、遮挡或通行。需要引擎验证时导出 Godot 并实际运行；脚本可布置对照样本，但不能因此声称 UI 操作或完整物理已验收。
6. 将有依据保留的版本通过项目引用选入对应需求；保留原图和来源，不覆盖旧包。说明实际保留哪些、淘汰哪些、为什么，以及产物位置和剩余限制。展示实际画面。只留下够用的记录，不以继续盘点替代生产。

## 结果与边界

- 历史/地域适用性依靠参考资料、提示词和人工判断；画风参考不是考证资料。
- 描述相同、带相同投影标签或使用共同参考，均不保证输出统一；查看真实图像。
- `complete` 是技术处理结果。清单里的 `production_ready:false`、`art_review:pending` 等按真实含义保留，不为了通过而改字段或放宽阈值。
- 连接构件需专项验证。单张篱笆不等于可拼围栏，桥 PNG 不等于可通行桥；人物、建筑模板、墙体和水岸使用专用流程，先查源码/现有文档，不能套普通物件接口宣称完成。
- 确认反复出现、且软件能解决的具体阻碍后再改 Studio。不要自动新增审核评分、历史验证、大地图或玩法系统。
