# Studio 操作逻辑审查

日期：2026-11-03。范围：项目清单与任务入口、候选挑选、组合、交付、人物动作与交付、物件设置、验证场景、删除。依据是当前代码、临时项目浏览器回归和已有实际人物的只读页面验证；未调用生图，未修改现有用户素材。不是所有素材类别的完整生产验收。

## 判断

问题的核心是同一件事在不同页面有不同规则：工作台处理当前成果，项目采用独立快照，场景引用固定版本；任务、候选、成果、已采用结果又经常共用入口。单纯删除折叠栏不能解决这种割裂。

优先保证三件事：点击的对象明确；预览、设置、采用和下载指向的内容明确；修改一次后，不要求用户在多个页面重复完成同一决定。

## 本轮已修正

| 问题 | 原有操作与后果 | 修正 |
| --- | --- | --- |
| 继续生产打开旧成果 | 已采用素材后再次生产，再点“制作 / 继续生产”，优先打开采用来源，难以找到新任务 | 继续生产优先最近关联任务；“查看选用来源”独立指向采用来源 |
| 人物任务丢失人物编号 | 从清单进入人物生产任务时可能只带 task，不带 character，人物页面可能打开浏览器上次选中的人物 | 任务入口同时传入 task 与 character |
| “设置生产”不进入生产 | 一键生产条件不满足时只弹出通用详情，还要再找工作台链接 | 改为直接“进入工作台”，清单卡片显示缺少条件的原因 |
| 临时候选阻止保存组合 | 存在任何临时候选就拒绝保存，要求逐个采用或取消 | 保存已采用素材的位置；候选仍只是预览，不被偷偷采用 |
| 设置改了却能采用旧结果 | 单动作修改颜色或精简但未点击更新，仍可点击“用于角色动作集”，采用的是旧结果 | 待更新时禁用采用，先完成更新 |
| 对照画面与采用对象不一致 | 正在看原色对照，但“用于角色动作集”仍采用处理后的成果 | 对照时禁用采用，并说明切回成果后再用 |
| 失败任务挡住可用交付 | 新一轮生产失败/运行中时，已有动作集的下载入口被隐藏 | 已有动作集有效就保持可下载，标为“下载已有动作集”，说明候选预览与下载对象的区别 |
| 调整单动作后整套无法下载却无即时提示 | 单动作换配色可能破坏动作集配色一致性，问题要回另一页才看到 | 单动作调整页直接显示动作集阻断错误；运行或失败状态也不再隐藏错误 |

最后一项只修复了反馈位置，尚未完成“整套配色统一修改”的产品逻辑，见下文。

## 尚未闭环，按优先顺序处理

| 优先级 | 问题与复现 | 实现依据 | 建议的最终规则 |
| --- | --- | --- | --- |
| P1 | 在工作台改好素材，项目仍下载旧快照；场景仍使用旧引用。人物 current 更新和项目快照也不会自动同步 | `studio_projects.source/change/select`、`scene_modules.pin/load`、`current_delivery.publish` | 素材设置保存后更新当前素材；采用该素材的项目/验证场景使用它的当前成果。独立已下载文件自然保留原内容。需要协调存储迁移，不能只改界面 |
| P1 | 人物单动作改颜色会使整套配色不一致，动作集被阻止导出 | `renderSheet`、`action_set.inspect` | 人物整体配色从整套入口修改；单动作页以预览和动作专用调整为主。不能偷偷放宽结构一致性要求 |
| P1 | 删除所有场景实例后仍不能删除素材，因为模块仍在场景模块列表中；界面只有删除实例，没有移除该模块引用 | `module-scenes.js remove`、`scene_modules.change`、`deletion.references` | 区分“删除摆放”与“从验证场景移除素材”；移除最后一个引用应能直接完成 |
| P1 | 从项目进入人物工作台后，没有与普通物件同样的成果采用入口，要回项目选择器再找到人物 | `navigation.js` 依赖 `studio:asset`；人物页面不发送相应可采用成果事件 | 当前人物成果就绪后直接“用于此需求”；已有采用应跟随当前成果，不重复选用 |
| P2 | 取消临时候选后，重新刷新组合页仍可能自动放回该候选 | `hub.js refresh/review` 为没有选用的需求自动 staged 最新结果 | 候选由用户显式加入比较，取消即退出；不在刷新时替用户重新选择 |
| P2 | 动作清单和整套输出参数只在内存草稿中修改，刷新页面可能恢复旧配置 | `productionDrafts`、`editProductionActions`、`productionDraft` | 调整设置自然保留为当前制作设置；避免再加一套版本、保存草稿按钮和确认流程 |
| P2 | 点一次整套交付会创建一份新 ZIP 和发布记录，内容未变也重复保留；历史交付仍展示给用户 | `studio_projects.release`、`hub.js delivery` | 下载当前成果，内容未变复用现有包；移除发布版本列表。需和项目当前成果模型一起改 |
| P2 | 普通物件保存锚点/碰撞仍创建新物件版本；同一个素材被不断复制，旧物件版本没有随当前模型一起清理 | `static_props.annotate/_publish_annotation`、`sprite-editor.js save` | 保存就是更新这份素材；“另存为新素材”才产生新的库对象 |
| P2 | 归档需求仍阻止删除素材，已归档界面却只有恢复按钮 | `deletion.references`、`hub.js archived_items` | 既有归档项提供直接删除；新流程以删除/移除为主，不继续扩展归档机制 |
| P2 | 项目生产完成要手动刷新；不少工作台本身又定时刷新，同样的“任务完成”体验不一致 | `hub.js` 无任务轮询，人物/物件等有轮询 | 项目内任务自动更新，但不能重建正在编辑的表单、重置候选或移动位置 |
| P2 | 单动作调整仍暴露采用槽位、原始批次渲染、质量记录、完整记录等内部概念；与整套生成入口并存 | `renderSheet/renderActionSetAdvanced/renderExport` | 主线只保留动作预览、实际可改设置和下载；需要重做时明确“重新制作当前动作”，不让用户选内部记录 |
| P2 | 从验证场景编辑素材，保存会更新当前场景引用，其他场景和项目不动；“保存素材设置”表达不出这个范围 | `scene_modules.change(module)`、公共静态素材编辑器 | 和当前素材模型统一；保存作用范围遵循稳定规则，而非取决于从哪个页面进入 |

## 实施顺序

1. 先统一“素材当前成果 → 项目需求引用 → 验证场景引用”的关系，明确更新传播和真正独立的素材对象。
2. 再收敛人物整套/单动作修改范围，解决一处调整破坏另一处交付的问题。
3. 补齐移除引用和旧归档项删除，让删除提示给出的处理方式确实可操作。
4. 最后删除不再需要的快照/发布/候选管理界面与中间记录，整理任务自动反馈。

不建议在旧关系上继续叠加“同步版本”“确认更新”“审核差异”等新步骤。上述剩余项未在本轮冒进迁移，避免把一次操作审查变成未经验证的全库数据重写。
