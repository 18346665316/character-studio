# Pixel Animation Studio：项目定位与功能梳理

更新：2026-11-03。基于当前代码、界面与已有验收资料梳理；本次未重新执行生产或引擎测试。本文区分现状与整理建议，不表示已经完成界面或架构调整。

后续首轮整理已实施：模块场景收进“验证工具”；普通素材成果页可直接采用到项目；动作与交付页移除人工检查记录、整套检查报告与高级管理，人工检查不作为验证场景准入门槛。下文第 6–8 节保留梳理时的问题与方向，具体改动与边界见[生产流程简化](studio-projects.md)。人物单动作手动颜色/帧精简已进一步改为替换当前成果，并移除历史恢复入口；其他生产线的存储迁移尚未完成。

## 1. 项目定位

核心是游戏素材生产：把需求、风格参考或外部素材转换为可挑选、可复用、可追溯、可交付的素材成果。

Godot 是当前的渲染工具和接入验证目标。模块场景、小院、宋村等用于验证素材的比例、连接、动画、碰撞、遮挡与交付契约；可玩流程用于暴露素材使用问题，不作为产品主线。

衡量项目进展应优先看：能稳定生产哪些素材、能否复用与修改、输出是否一致、交付能否独立接入，以及失败后是否可以恢复。演示地图大小和游戏玩法数量不作为素材生产能力的完成指标。

主流程：**素材项目与共同基准 → 需求清单 → 生成或导入 → 后处理与设置 → 候选比较与采用 → 独立或整套交付 → 使用验证与反馈。**

## 2. 功能归属

| 层次 | 负责什么 | 当前对应实现 |
| --- | --- | --- |
| 素材生产 | 各类素材的输入、生成、后处理和专用输出 | 人物、地表、道路、水体、物件、连接构件、建筑工作台 |
| 共用支撑 | 项目基准、需求、任务、来源、版本、素材查找、选用与交付 | `studio_projects.py`、`asset_repository.py`、图片服务、任务锁、各类包校验 |
| 成果验证 | 单项检查、视觉组合、拼装、引擎接入及真实使用反馈 | 组合挑选、模块场景、Godot 验收工程、演示工程 |

素材上的锚点、尺寸和碰撞设置属于素材接入数据；验证场景负责引用这些数据。验证过程中发现设置有误，应回到素材版本中修正，再显式替换引用。

## 3. 素材生产能力现状

“已实现”表示存在实现路径，不表示所有素材均已通过美术验收，也不表示已经达到正式生产就绪状态。

| 素材类别 | 现有生产能力 | 主要成果 | 当前限制或待验收项 |
| --- | --- | --- | --- |
| 人物与动作 | 原画重建或外部 GLB 导入、模型准备与减面、Mixamo 辅助绑定和动作下载、Godot/Blender 渲染、时序精简、共享调色板、动作集生产 | 图集、逐帧时序、预览、动作集、Godot 人物包及使用契约 | 绑定仍有人工作业；动作语义、朝向、循环接缝、轮廓稳定性和风格适配需要复核 |
| 武器与装备 | 独立武器输入与重建、握持标注、持用/收纳配置、随人物动作渲染 | 装备配置及带装备的人物成果 | 属于人物生产的配套能力；依赖绑定与动作，不能视为完整装备玩法系统 |
| 独立地表 | AI 材质或图片导入、平铺处理、变化组、部分规格的等距投影 | 地面瓦片、图集、预览、清单和来源 | 重复感、纹理尺度和画面一致性仍需目视检查 |
| 地表过渡 | 复用两份地表，按共享角点生成 16 种组合与变化组；已有等距投影实现 | 过渡瓦片、图集、角点规则及来源包 | 不是通用地形编辑器；场景绘制、变化组自动分配等能力尚不完整 |
| 道路 | 地面与道路材质输入、固定宽度、四方向连接与自然边缘 | 道路连接块、透明道路层、图集及连接清单 | 当前支持正俯视道路；项目中的等距道路生产会拒绝 |
| 静态水体 | 独立水面、陆地与水面的湿岸/浅水过渡、水域覆盖遮罩 | 水面与水岸素材包；部分新过渡包带保守阻挡代理 | 不含动态水面、深度或流场；不能假定所有历史水岸包都有碰撞 |
| 独立物件 | 石头、木箱、灌木、自定义物件的 AI 生成或导入、透明处理、裁切、规格化和重新后处理 | 透明 PNG、预览、来源、锚点、基准比例、可选多块凸碰撞 | 单色背景处理不是语义分割；镂空/细叶等仍受限制；接触面和占地需人工判断 |
| 连接构件 | 木纹生成或导入、程序构造围栏模块、接口、建议碰撞及部分深度分层 | 12 模块围栏候选、图集、接口、组合样例和 ZIP | AI 目前提供木纹；完整四向墙门套件、可靠拼接与复杂遮挡尚未闭环 |
| 建筑 | 框线图定义形体，AI 生成外观、候选比较、透明处理、人工锚点/占地标注；可适配到公共物件版本 | 独栋建筑透明图、来源、标注与独立包 | 视角与结构仍需目视复核；单图长建筑的遮挡和多层空间未解决 |

## 4. 共用能力现状

| 能力 | 当前情况 | 需要梳理的重点 |
| --- | --- | --- |
| 素材项目 | 共同风格、配色、光照、视角、相机/朝向说明、地格与人物高度、需求清单 | 共同基准在不同生产线中的执行程度不同，提示词继承不等于输出一致 |
| 生成与导入 | 各工作台支持不同输入；部分清单可直接生成 | 清楚展示每类支持的模式、前置条件和规格，避免让用户到工作台后才发现不支持 |
| 图片服务 | 兼容接口和 Google Cloud；配置、请求记录与恢复机制 | 属于设置与任务支撑，不能成为生产主流程的中心 |
| 任务 | 后台执行、持久记录、部分断点复用、错误与请求日志 | 多类任务实现并存；当前单生产锁，没有整套自动排队生成 |
| 素材查找与复用 | 项目候选选择器、各工作台历史、模块场景素材选择器 | 功能存在，但尚未形成一致的素材浏览、筛选和版本关系体验 |
| 版本与来源 | 多类不可变成果、来源指纹、项目选用快照、修订冲突检测 | 各类字段和验收状态表达不统一；人物动作、静态物件、套件各有契约 |
| 素材设置 | 公共静态素材编辑器支持锚点、等比尺寸、多块凸碰撞；人物有独立动作与锚点契约 | 统一入口含义和单位，不强行把所有素材压成同一种数据结构 |
| 候选采用 | 比较候选、采用版本、保存快照，不自动改写旧交付 | “采用”只表示选择，不应暗示美术或引擎验收通过 |
| 交付 | 单项 ZIP、人物 Godot 包、整套项目包、验证场景工程 | 产品首先交付独立素材；验证工程是额外证据与接入样例 |

## 5. 三种预览与验证应各司其职

| 工具 | 回答的问题 | 应记录的结果 |
| --- | --- | --- |
| 工作台预览 | 单个成果的外观、透明边缘、动作或连接规则是否合适？ | 候选版本、生成参数、设置和单项检查 |
| 项目组合挑选 | 同一项目中的风格、比例、配色、视角是否协调，采用哪个版本？ | 采用快照、对照位置/显示比例和备注 |
| 模块场景与 Godot 验证 | 多个素材在实际使用中能否连接、阻挡、通行、排序并正确播放？ | 引用版本、测试布局、运行报告、截图及未通过问题 |

当前模块场景已有摆放、重复实例、吸附、撤销重做、出生点、素材设置与 Godot 导出，因此很容易向地图编辑器扩展。保留这些能力的理由应是可重复验证素材，而不是继续建设游戏制作工具。

宋村中的任务、采集、交谈、存档和 UI 属于验证消费者。NPC 的 idle/talk 播放可以验证人物包，任务路线可以验证通行，但任务系统本身不属于 Studio 素材功能。

已有验收结果只覆盖相应素材版本、布局和条件。某个 Demo 能完成任务，不代表其素材已经普遍可用。

## 6. 当前最需要解决的混杂与缺口

1. **生产结果与验证结果混在一起。** 建筑能生成、能导出、能进入宋村、能正确遮挡是不同结论。目前散落的说明容易让“已有演示”覆盖掉尚未解决的素材问题。
2. **素材设置入口分散。** 物件、建筑和场景均涉及锚点/占地，场景编辑窗口已经复用公共编辑器，但用户仍容易把它理解为“为这一张地图临时修素材”。应明确设置发布为哪个素材版本、影响哪些引用。
3. **视觉比例存在两种语义。** 项目组合的显示比例用于比较；素材的 `world_scale` 用于接入。二者不应在交付时被误认为同一个设置，也不能靠验证场景偷偷修正实际尺寸。
4. **库与类别适配不齐。** 模块场景代码已有物件、地面、过渡、建筑桥接和人物接入，而页面说明仍写着建筑未适配；围栏套件仍不等于单图物件。需要按具体支持范围说明。
5. **文档落后于实现。** 资产规范仍含“物件宽深椭圆”“水体无碰撞”等早期描述；新实现已有多区域标注和部分水岸阻挡代理。应注明版本与适用范围，不能直接推广到旧素材。
6. **连接类素材缺少完整生产闭环。** 小院已验证出墙段方向、墙门斜率/高度、接缝和整图排序问题。应回到构件规格与生产验收解决，不能用布局或玩法掩盖。
7. **主文档按功能追加，缺少总览。** README 同时承载用户入口、运行环境、实验记录与技术限制，读者难以判断主流程及功能成熟度。

## 7. 建议的产品组织

以下为整理方向，尚未改动现有导航与代码。

- **素材项目**：共同基准、需求清单、进度与选用情况。
- **素材生产**：从需求进入专用工作台，完成输入、生成/导入、处理、候选和设置。
- **素材库**：一致地查找成果、查看来源/版本、复用和下载；可先统一选择体验，不要求立即迁移存储。
- **组合挑选与交付**：同风格比较、采用快照、检查缺项、导出独立或整套素材。
- **验证工具**：模块拼装、人物接入、地表/道路、水岸、围栏等固定验证入口，以及实际演示工程。

验证工具作为辅助入口。当前模块场景处于主导航；是否调整位置，应在梳理后的界面方案中明确实施，而不是把现状描述成已调整。

## 8. 后续工作的顺序

| 优先级 | 工作 | 完成标准 |
| --- | --- | --- |
| P0 | 统一项目定位、功能清单和状态说明 | 首页/主文档能说明生产什么、怎么交付、哪些能力有限制；验证与玩法职责清楚 |
| P1 | 梳理各类生产闭环与素材版本体验 | 每类均能说明输入、规格、候选、可修改设置、采用、交付及失败恢复；没有能力的环节明确标出 |
| P1 | 统一素材规格与验收记录的表达 | 视角、尺寸、锚点、时序/连接/碰撞、来源指纹和验收范围可查；保留类别专用字段 |
| P1 | 修复已被验证暴露的素材问题 | 优先处理比例、构件方向与接缝、透明边缘、动作一致性、遮挡等实际问题，并保留复验样例 |
| P2 | 整理验证入口与历史演示 | 明确每个样例验证什么、使用哪个版本、如何复验；避免同一职责重复建设 |
| 按需求推进 | 队列、更多类别或自动化 | 在现有生产闭环稳定后，根据实际重复操作与生产需求决定 |

近期不以新增采集、战斗、经济、地图内容或更复杂的游戏 UI 作为 Studio 迭代目标。
